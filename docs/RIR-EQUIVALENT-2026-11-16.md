# RIR-эквивалент на TU102: что построено, что проверено, где стена (2026-11-16)

Задача: повторить на CMP 50HX приём GA100 — снять запрет software-override,
который там снимают прожигом RIR-записей, — и довести до работающего результата.

**Итог: механизм прожига на TU102 недоступен; программного эквивалента, который
включал бы NVLink, не существует. Всё, что можно было проверить программно, —
проверено, с отрицательным контролем.**

## 1. Можно ли вообще прожигать записи (read-only)

Инструмент `/data/build/parity/rir_probe.c` (mmap `resource0`, только чтение).
Вывод на `05:00.0`:

```
FUSECTRL        0x21000 = 0xc0040000  CMD=0 STATE=4 SENSE_DONE=1
EN_PROGRAM      0x21078 = 0xbadf5040  POISON (gated)
DIS_PROGRAM     0x2107C = 0xbadf5040  POISON (gated)
BYPASS_STATUS   0x21080 = 0xbadf5040  POISON (gated)
EN_SW_OVERRIDE  0x21040 = 0x00000000  0
DIS_SW_OVR      0x21084 = 0xbadf5040  POISON (gated)
record ptr A    0x21068 = 0x00021e3c -> 0x00000000
record ptr B    0x2106C = 0x00021f94 -> 0x00000000
PROGRAMMING PATH: GATED
```

То же в pre-OS дампе: слова `0x21020..0x2108F` — poison и в окне ботера.
**Прожиг фьюзов/записей на TU102 недоступен ни из ОС, ни из EFI.**

## 2. Что пробовали вместо прожига (три one-shot прогона + контроль)

| # | слот #1 | слот #2 | результат |
|---|---|---|---|
| 1 | XP3G-гейт (контроль) | `EN_SW_OVERRIDE 0x21040 <- 1` | **ACCEPTED**, readback `1` (было `0`) |
| 2 | `EN_SW_OVERRIDE <- 1` | `FUSE_NVLINK_DIS 0x21684 <- 0` | гейт `1` (LANDED), теневой фьюз — **REFUSED** (`0x1` остался) |
| 3 | `EN_SW_OVERRIDE <- 1` | `CTRL_OPT_NVLINK 0x219B8 <- 1` | **ACCEPTED** |
| 4 | XP3G-гейт (контроль) | `CTRL_OPT_NVLINK 0x219B8 <- 2` **без** гейта | **ACCEPTED** ← отрицательный контроль |

Прогон 4 — ключевой: слово `0x219B8` пишется **и без** открытого гейта. Значит
это просто писабельный регистр, а не «слой, который открывает гейт». Гипотеза
«гейт разблокирует override-слой» **опровергнута собственным контролем** — иначе
я бы записал в отчёт неверный вывод.

## 3. Что из этого следует

1. **Фьюз-тень NVLink не пишется** (`0x21684 = 0x1` даже при открытом гейте), и по
   модели GA100 эффективное состояние = `OPT | (CTRL & ~OVR)` — установленный бит
   фьюза CTRL не отменяет.
2. **Таблица движков — ROM** (доказано ранее): IOCTRL не перечисляется, подделать
   нельзя.
3. **Прожиг недоступен** (см. §1). На GA100 именно он маскирует фьюз и открывает
   перезаписываемый слой; на TU102 этого интерфейса нет.
4. Писабельные, но безрезультатные слова (`EN_SW_OVERRIDE`, `0x219B8`) на
   эффективное состояние не влияют: после записи `CTRL_OPT_NVLINK` движок в
   топологии не появляется.

**Вывод: «RIR-эквивалент», который включал бы NVLink, на TU102 построить нельзя.**
Единственный оставшийся путь — аппаратный (сбой чтения фьюзов на POST), и он
требует жертвенной карты: прожига нет, значит и «испортить запись» нечем — но и
включить нечего, пока фьюз читается как 1.

## 4. Практическая ценность проделанного

- `rir_probe` одной read-only командой отвечает на вопрос «есть ли путь
  программирования фьюзов» — теперь ответ зафиксирован и воспроизводим.
- Отрицательные контроли закрыли две ложные ветки: «гейт разблокирует слой» и
  «CTRL_OPT включает NVLink».
- Для **других** фьюз-гейтов, у которых есть парный feature-override (ECC и
  подобные), путь остаётся: писать не фьюз, а override-регистр (как SS0/SS1 в
  compute-unlock). Это отдельная задача и она не про NVLink.

## 5. Repro

```bash
# «можно ли прожигать» — read-only
./rir_probe 0000:05:00.0

# гейт
EXTRA_CFLAGS='-DGEN3_SLOT2_ADDR=0x21040u -DGEN3_SLOT2_VALUE=1u' bash build.sh
# гейт + тень фьюза
EXTRA_CFLAGS='-DGEN3_SLOT1_ADDR=0x21040u -DGEN3_SLOT1_VALUE=1u \
              -DGEN3_SLOT2_ADDR=0x21684u -DGEN3_SLOT2_VALUE=0u' bash build.sh
# контроль: CTRL_OPT без гейта
EXTRA_CFLAGS='-DGEN3_SLOT2_ADDR=0x219b8u -DGEN3_SLOT2_VALUE=2u' bash build.sh
```

Логи: `/data/build/parity/50hx_log.rir-gate.txt`, `50hx_log.ctrl-negative.txt`.
Каждый прогон — one-shot, запись удалена; после каждого: обе карты Gen2, 7/7
сервисов, 0 Xid.
