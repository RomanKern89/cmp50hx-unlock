# NVLink reference data from public sources (2026-11-16)

Задача: найти в интернете эталон — fuse/register-значения TU102 с живым NVLink —
и извлечь из него то, что нужно для Трека F (`GLITCH-FEASIBILITY-PLAN-2026-11-16.md`).

## Что нашлось (сырые дампов TU102 в публичном доступе НЕТ)

| источник | что даёт |
|---|---|
| [GA100 Fuse & Register Reference Table (nvlight gist)](https://gist.github.com/nvlight/813a866dc69d417497a427f4208321ff) | 120 регистров по 11 картам Ampere, **с точными именами и смыслом** NVLink/PCIe/ECC фьюзов, включая значения на картах с NVLink (A100/A6000/3090 = `0x0`) и без (3080/3080Ti = `0x1`, 170HX = `0x7`) |
| [CMP Wiki — Unlock internals](https://cmp.wiki/wiki/Unlock_internals:_detailed_research_notes) | модель гейта (OTP-фьюзы → «fuseless» override-слой → RIR-записи), подтверждение, что запись OPT-фьюзов из BAR0 не работает, и что 170HX-NVLink «fuse-killed, silicon intact» |
| `open-gpu-kernel-modules` `tu102/dev_fuse.h` | единственные опубликованные TU102-фьюзы: `SECURE_GSP_DEBUG_DIS 0x2174C`, `NVDEC_DISABLE 0x21378` |

Ключевая цитата эталона: `FUSE_NVLINK_DIS`: **`0x0` = NVLink есть**, `0x1` = нет
(3080/3080Ti), `0x7` = все группы убиты (170HX), при этом `DEFECTIVE = 0x0` —
«silicon intact, just fuse-gated».

## Как перенесено на TU102 (и чем проверено)

Опубликованной карты для Turing нет, поэтому адреса получены привязкой страниц
по единственному общему регистру — `NVDEC_DISABLE` (GA100 `0x820378`, TU102
`0x21378`), сдвиг `0x7FF000`:

`TU102_адрес = GA100_адрес − 0x7FF000`

Проверка **независимыми фактами, которые мы уже доказали сами**:

| регистр | TU102 | у нас | что говорит эталон | вывод |
|---|---|---|---|---|
| `OPT_DISABLE_GEN3_SPEED` | `0x21250` | **0x1** | bit0=1 на всех стоковых CMP | ✅ Gen3 заперт |
| `FUSE_PCIE_GEN3_DIS` | `0x21580` | **0x1** | 1 на стоковых | ✅ Gen3 заперт |
| `OPT_ECC_EN` | `0x21228` | **0x0** | 0 на стоковых CMP | ✅ |
| `FUSE_NVLINK_DEFECTIVE` | `0x2168C` | **0x0** | 0 на всех | ✅ кремний цел |
| `FUSE_EN_SW_OVERRIDE` | `0x21040` | **0x0** | 0 на 170HX/A100 (override-гейт закрыт) | ✅ совпадает с нашими отказами записи |
| `FUSE_FEAT_OVR_DIS` | `0x213F0` | **0x0** | 0 на всех | ✅ override-класс не убит мастер-фьюзом |
| `FUSE_PCIE_GEN23_DIS` | `0x2157C` | 0x0 | 1 на стоковых 170HX | ⚠️ расхождение объяснимо: у нас Gen2 политикой достигается, «Gen2+Gen3 boot disabled» не взведён |
| **`FUSE_NVLINK_DIS`** | **`0x21684`** | **0x1** | `0x1` = NVLink нет, `0x0` = есть | 🎯 **целевой бит найден** |

Итог: **`BAR0 0x21684 = 0x1`** — это фьюз, которым на CMP 50HX выключен NVLink.
Шесть из восьми ожиданий совпали точно, седьмое объяснимо, восьмое (NVLink) —
и есть искомое. Кремний не помечен дефектным (`0x2168C = 0`), то есть блок на
кристалле есть, он именно зафьюжен.

## Что из эталона следует для стратегии

1. **Запись фьюзов из BAR0 мертва** — в эталоне это отдельно зафиксировано
   («K2V: no effect… values can be written but are ignored»), и наши три отказа
   (`0x21378`, `0x823810`, PTOP) — то же самое. Эталон добавляет важное: из BAR0
   меняются только OPT-фьюзы, **у которых есть парный feature-override регистр**
   (пример — ECC). У NVLink на нашей карте такого окна нет: страница `0x8238xx`
   читается как poison, что мы проверили.
2. **Override-гейт закрыт**: `EN_SW_OVERRIDE = 0` — тот же класс, что 170HX/A100.
   На GA100 его открывали **прожигом RIR-записей** (2 записи, `0x00150095`), после
   чего работал перезаписываемый «fuseless» слой. Для TU102 публичных данных о
   RIR-эквиваленте нет; отдельно известно, что прожиг необратим.
3. **NVLink — тот же паттерн, что и на 170HX**: «fuse-killed, silicon intact».
   Публичный результат по 170HX получен **hardware-путём** (инжекция сбоя по
   фьюзам + доработка платы), а не софтом; на 8-гигабайтной карте вики прямо
   пишет «no path».

## Чего не хватает (честно)

- **Сырого дампа TU102 с рабочим NVLink** (2080 Ti / Titan RTX / Quadro RTX) в
  интернете нет — ни gist, ни форумы, ни nouveau такого не публикуют.
  Наша привязка подтверждена косвенно (6 независимых значений), но не прямым
  сравнением. Один взгляд на `0x21684` у 2080 Ti (`0x0`) закрыл бы вопрос.
- Для глитча нужен **целевой класс**: убедиться, что `0x21684` — OTP-фьюз, а не
  «fuseless»-слой. По эталону `FUSE_NVLINK_DIS` живёт в том же блоке OPT, что и
  `FUSE_PCIE_GEN3_DIS`, а он на 170HX **не поддался** ни BAR0, ни firmware —
  значит это прожиг. Для глитча это, впрочем, даже полезнее: глитчить надо
  **чтение фьюзов на POST**, а не запись.
