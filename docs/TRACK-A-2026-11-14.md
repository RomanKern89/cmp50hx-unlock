# Track A — consolidation of the Gen2 unlock (2026-11-14)

Follow-up to `GEN3-PROBE-RUN-2026-11-14.md`: with Gen3 closed by hardware, this
is the mandatory consolidation track from `ACTION-PLAN-2026-11-14.md`. Executed
on lmserver (`192.168.1.215`, ASUS X99-E WS, 2× CMP 50HX behind dual PEX8747).

## A1. Code ↔ production parity — a real gap found

Built the committed `master` for kernel `7.0.0-42-generic` on the host (cached
610.43.03 source, `build.sh --card cmp50hx`) and compared with the running module.

| check | result |
|---|---|
| `vermagic` | identical (`7.0.0-42-generic SMP preempt mod_unload modversions`) |
| markers `CMP50_COMPUTE_UNLOCK` / `CMP50_GEN2` / `CMP50_STOCKFLOW` / `UPSTREAM_RETRAIN` / `ALREADY_GEN2` / `ADOPT_FAIL` | 30 / 18 / 18 / 3 / 1 / 1 — identical counts |
| module parameters | **differs**: production has `cmp50_rebar_size`, `cmp50_gen2_adopt`; `master` adds `cmp50_target_gen` |
| `.text` hash (debug stripped) | differs for `nvidia.ko`, `nvidia-uvm.ko`, `nvidia-modeset.ko`; identical for `nvidia-drm.ko`, `nvidia-peermem.ko` |
| module installed for `7.0.0-43-generic` | **bit-identical `.text`** to a fresh build from `master` (before the fix below) |

Conclusion: the production module was built from a pre-adaptive working tree (the
one the plan flagged as unverified), while `master` carried commit `79919bb`
("make the PCIe link unlock generation-adaptive") that was never proven on
hardware.

## A2. The regression in `79919bb`, and the A/B that found it

Booted the master-built module on **both** kernels:

| boot | module | result |
|---|---|---|
| 7.0.0-43 + master (as installed 16:40) | `cmp50_target_gen=3` | `ADOPT_PASS target=Gen2 adopted=Gen2` → **`RETRAIN_FAIL status=1081 ret=0`**, both cards at **Gen1** 2.5 GT/s |
| 7.0.0-42 + master | same | **identical failure** — so it is the code, not the kernel |
| 7.0.0-42 + production module | pre-adaptive code | `RETRAIN_PASS mode=normal status=1102 attempt=1`, Gen2 |

The retrain body is the same in both versions; the only difference is the policy
generation written into the XVE fields (`CFG0` bits 19:18, `PL_RATE` bits 18:17):
`79919bb` writes the *requested* generation (default **3**) instead of the proven
**2**. With the Gen3 policy the retrain pulse ends at Gen1 and never recovers.
`docs/PCIE-GEN3.md` already claimed "the generation request defaults to Gen2",
so the code was simply out of line with its own documentation.

Fix (`b74f44c` + `0c0cebf`):

- `patches/cmp50hx/04-cmp50-pcie-gen2.patch`: `cmp50_target_gen = 2` (default),
  with a comment recording the measurement; Gen3 stays an explicit knob.
- `cmp50hx/cmp50hx-gen2.sh`: `CMP50_TARGET_GEN` default 2, header comment fixed.
- hunk line count in patch 04 corrected (the added comment shifted it).
